## Count comparison and overall judgment

The original ER sketch has **12 conceptual entities**, not twelve implemented tables. The revised specification has **17 proposed tables: 16 core and one conditional activity table**. It includes 13 domain/lookup components and four source/access support tables, while the original omitted implemented provenance, authorization and restricted-data separation. Thus the full count increases by five for explicit integrity/security requirements. Table-count reduction is not a goal by itself.

Retain the meaningful source grains. Simplify by replacing the program-only lookup with one scoped reference table, removing independent redundant child/caregiver IDs from questionnaire responses, avoiding copied current names on facts, not persisting unapproved totals/ages or a duplicate joining-year attribute, and preventing separate summary/tab-specific business tables. Add typed answer values, a real pair FK, protected child attributes and bounded provenance. Do not merge caregivers with relationships before identifier scope is approved.

## Missing relationships and normalization corrections

1. Independent questionnaire child/caregiver FKs do not enforce the observed pair. The association FK does, and removes repeated ID fields from the curated submission.
2. Responses and answer items must share an approved definition. Composite definition-key FKs prevent cross-definition answers without adding a generic questionnaire engine.
3. Lookup IDs/codes require vocabulary integrity; a plain FK to a universal lookup ID is insufficient. Fixed server-generated vocabulary discriminators plus composite FKs are proposed.
4. Imported targets need many-source provenance. A single origin string or unconstrained entity_type/entity_id pointer cannot preserve merged field lineage or SQL FK integrity. One bounded typed-target provenance table is proposed instead of one provenance table per domain entity.
5. Missing/ambiguous child references cannot be promoted into authoritative facts by fuzzy matching. Staging is a distinct state, not silent data loss.
6. A private child profile is a permission boundary, not a new NGO entity. Children/caregivers themselves still contain personal names and remain RLS protected.

## Complexity not introduced

No household, sibling-person, staff, generic service session, payment transaction, date-dimension, diagnosis ontology, metric-definition engine, per-worksheet table or computed-score fact table is justified now. These can be reconsidered only against approved workflows/source evidence. A sibling header template and fee summaries are retained, not converted into invented people/payments. The 17-table total excludes Supabase-managed `auth.users`; no separate login-identity copy is created.

## Risks and approval gates

Source retention alone is not typed operational coverage: 1,820 column positions currently have no named business projection, explicitly listed in the mapping matrix. Most are summaries, blank/technical columns, alternate views or conditional activities/templates; any required workflow among them must receive an approved projection before implementation. Other risks are unresolved identity scope, proposed lookup changes, incomplete source event grain, date sanitization that does not preserve chronology, and lack of empirical database performance measurements. Technical checks do not resolve any of these business questions.

All revisions are draft. The [decision register](13-data-quality-decision-register.md) and [acceptance criteria](14-project-standards-and-acceptance-criteria.md) govern the next approval; they do not authorize SQL or migration.
